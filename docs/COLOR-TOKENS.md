# 颜色 token 化方案清单（2026-10-21 实测）

> 夜星要求「先列一份哪些颜色能安全映射到现有 token 的清单」。
> 本文所有数字都是脚本实测（正则扫 `src/**/*.vue` + `src/**/*.css`，排除 token 定义行），不是估算。

## 一、结论先行

**不建议直接开始「把硬编码色换成 var(--token)」。**

实测发现真正的问题不在调用点，而在**色板本身已经分裂**：

| 指标 | 实测值 | 含义 |
|---|---|---|
| token 定义总数 | **693** | 数量已超过可用心智 |
| 并行色板族 | **14 个**（`--el-*` 222 / `--color-*` 104 / `--m-*` 69 / `--xz-*` 64 / `--yq-*` 53 / `--ls-*` 40 / `--dp-*` 38 / `--tc-*` 31 / `--lj-*` 28 / `--xiu-*` 27 / `--ink-*` 17 / `--ab-*` 14 / `--island-*` 12 / `--li-*` 12） | 同一语义有 3-5 个名字 |
| 不同色值 | 405 | — |
| **被多个 token 重复定义的色值** | **135** | 例如 `#c7a96b` 同时是 `--yq-gold` / `--ls-ochre` / `--yq-gold-bright` |
| 调用点硬编码色 | **2241 次** | 其中游戏美术类 **1006 次**（不应 token 化） |

### 为什么不能直接替换：两类「多值」必须分开看

先澄清一个容易误判的点 —— **同名 token 有多个值，不一定是问题**：

| 类型 | 例子 | 判定 |
|---|---|---|
| **主题差异（正常）** | `--tc-cyan`：夜 `#2de2ff` / 日 `#0a708c` | 设计意图，夜间亮青、日间深青 |
| **同族冲突（真债）** | `--yq-gold`：`variables.css` = `#c7a96b`(金) / `tech-theme.css` = `#2de2ff`(青) / `desktop-theme-day.css` = `#fbbf24`(黄) | **同一个名字四种色相**，不是主题差异 |

实测全部冲突项：

| token | 各文件取值 | 冲突程度 |
|---|---|---|
| `--yq-gold` | `#c7a96b`(金) / `#2de2ff`(青) / `#0a708c`(青) / `#fbbf24`(黄) / `#a9804f`(褐) | **5 个值，4 个色相** |
| `--xz-gold` | `#c9a45c`(金·移动端) / `#2de2ff`(青·桌面夜) / `#0a708c`(青·桌面日) | 移动端金、桌面青 |
| `--color-gold` | `#c9a96e`(金) / `#2de2ff`(青) / `#0a708c`(青) | 同上 |
| `--lj-seal` | `#d98a76`/`#c25e4c`(暖红) / `#0a708c`(青) | 印章色 vs 青色 |
| `--dp-up` | `#e5484d`/`#c93a3f`/`#cf2540`/`#ff4d6d` | 语义一致（涨），但四个红各不相同 |
| `--tc-cyan` | `#2de2ff` / `#0a708c` | ✅ 正常主题差异 |

**这直接否掉了「按色值机械替换」这条路**：
`#c7a96b`（金）唯一映射到 `--yq-gold`，但在 `tech-theme.css` 生效的环境里 `--yq-gold` 是青色 ——
替换完，金色会变青。

所以顺序必须是：**先分清"该跟随主题"还是"必须固定" → 再动调用点**。

### 由此得出更安全的替换原则

替换不是「色值 → 同名 token」，而是先做**语义判断**：

| 场景 | 正确做法 |
|---|---|
| 这个颜色**应该**随昼夜切换（正文、卡片底、边框） | 替换成主题 token |
| 这个颜色**必须**恒定（鎏金描边、品牌色、棋子） | 新增固定色 token（如 `--c-gold: #c7a96b`），不挂主题 |
| 已经有矛盾 token 名的地方 | 不替换，等阶段 3 改名后再处理 |

这就是为什么阶段 0 要先建映射表 —— 映射表的核心列不是「色值→token」，而是**「色值→语义→是否跟随主题」**。

## 三、明确不做的部分（1006 次）

游戏/美术类文件：`RoadRashGame`(220) / `LudoBoard`(92) / `games3d.css`(71) / `GomokuBoard`(59) / `JunqiBoard`(58) / `MonopolyBoard`(58) / `XiangqiBoard`(57) / `GameTableView`(54) / `XiangqiFlipBoard`(52) / `GamesView`(52) …

这些是**美术资源色**（棋盘木纹、棋子配色、路面材质），不随主题切换，塞进主题 token 反而会破坏美术一致性。**保持硬编码。**

## 四、建议的四阶段计划

| 阶段 | 内容 | 改动面 | 风险 | 验收 |
|---|---|---|---|---|
| **0. 建语义映射表** | 每个高频色标三列：色值 / 语义 / **是否跟随主题**；同时提炼 10-15 个固定色 token（新增，不改旧） | 1 个 css + 本文件 | 低 | 视觉零变化 |
| **1. 替换「该跟随主题」的** | 从 A 类里挑语义明确的那部分（正文/背景/边框），逐处判断 | 约 15-20 个文件 | 中 | 4 主题 × 8 页面截图比对 |
| **2. 替换「必须固定」的** | 鎏金/品牌色走新增的固定 token（如 `--c-gold`），数量最大（214+） | 约 20 个文件 | 中低 | 同上，重点看换肤后金色是否仍为金 |
| **3. B 类定语义** | 4 个多候选色人工决策，写成规则 | 4 色 | 中 | 4 主题比对 |
| **4. 收敛色板 + 改名** | 135 个重复值合并；把 `--yq-gold`/`--xz-gold`/`--color-gold` 这类「名字叫金值是青」的命名债改掉 | 主题文件 | **高** | 全站 4 主题 × 全页面截图 |

> 阶段 2 排在阶段 3 之前是刻意的：**先把"必须固定"的色抽成固定 token，
> 后续收敛主题色板时，这些地方就不会被误伤。**

**阶段 1 的前置条件**（不满足就会翻车）：
1. 每个待替换点先回答「这个颜色应不应该跟着换肤」；
2. 目标 token 在各主题文件里的取值必须已核对（实测 `--yq-gold` / `--xz-gold` / `--color-gold`
   在同族不同文件里是不同的色相，见上表）；
3. 一个文件改完立刻在夜/日两个主题下各看一眼，不要批量改完再统一验。

## 五、验收方式（可量化，不靠肉眼）

每阶段改完：
1. 脚本复算「剩余硬编码次数」与「剩余孤儿色数」，与上阶段对比（本文件即为基线）；
2. 4 个主题 × 8 个代表页面截图，取 3 个关键色做像素采样比对（背景/正文/强调）；
3. 记录「本次替换 N 处 / 新增 token M 个 / 遗留 X 处」，写进 CHANGELOG。

### 🔴 重大发现：210 处里 167 处不是"硬编码"，是「挂错 token」

统计修正了原计划的假设：

| 形态 | 次数 | 说明 |
|---|---:|---|
| 纯硬编码（`background: #c7a96b`） | 21 | ✅ 本次已替换 |
| **`var(--yq-gold, #c7a96b)` 的 fallback** | **141** | 主 token 是**青色**，fallback 才是金 |
| `var(--color-accent, #c7a96b)` | 20 | 待查 `--color-accent` 实际值 |
| `var(--lj-ochre, #c7a96b)` | 6 | 待查 |

也就是说：**这 167 处本来就已经在用 token，问题不是"没抽象"，而是"token 指错了"**。
它们当前实际渲染的是青色（`--yq-gold` 在 tech-theme = `#2de2ff` / day = `#0a708c`）。

**修法完全不同**：
- 不是「色值 → token」替换；
- 而是「`var(--yq-gold, #c7a96b)` → `var(--c-gold)`」，**会把青变成金**（可见变化）。

### 需要拍板的问题

这 167 处（抽样看过：标题文字、按钮主色、描边、渐变起点，语义都是"鎏金装饰"）：
- **A. 改成金色**（`--c-gold`）→ 符合原始意图（fallback 写的就是金），但页面会和现在不一样；
- **B. 保持青色** → 那就该把 fallback 里的 `#c7a96b` 改成 `#2de2ff`，让代码与实际一致；
- **C. 分页面看** → 有些地方青色更好看（工具类页面偏科技感），有些地方该是金（生活/记账）。

**在拍板前不动**，避免制造意外视觉变化。

## 十、阶段 1 方案 B 执行结果（2026-10-21，v2.46.166）

夜星选择 **B：承认青色、不改视觉**。

### 做法：删掉失效的 fallback，而不是把金色改成青色

原提议是「把 fallback 的 `#c7a96b` 改成 `#2de2ff`」。实际执行时改了主意，理由：
`--yq-gold` 在项目里有 **12 处定义**（覆盖夜/日/移动/AB 各主题），
所以 `var(--yq-gold, #c7a96b)` 里的 fallback **永远不生效**，是死代码。
写死 `#2de2ff` 也不对 —— 日间该 token 是 `#0a708c`，硬编码任何一个值都不准确。

**正确处理：直接删掉 fallback** → `var(--yq-gold)`。
这既让代码与实际一致（跟随主题），又消除了「写着金色其实显示青色」的认知陷阱。
